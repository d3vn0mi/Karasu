Three wired roles, one box

One portable Raspberry Pi — a Wi-Fi AP, a wired drop, and the updrop file server — in three mutually-exclusive wired modes. The Wi-Fi + drop stay constant; only the wired role changes. Pick a mode, or compare all three.

AP mode

pi_ap_dropbox_setup.sh

The Pi is the network: clients connect to it, it hands out addressing and serves the drop. Isolated by default; optional NAT to an uplink.

drop / updrop internet / NAT
  • Clients → drop. Laptops on Wi-Fi (wlan0) and a workstation on a direct cable (eth0) reach updrop at karasu / .local / IP. Isolated mode stops here — no gateway, no internet.
  • Clients → internet (shared only). share on makes the Pi the gateway+DNS and NATs one MASQUERADE out the uplink.

Bridge mode

pi_bridge_setup.sh

Transparent bump-in-the-wire. Forwards the server's frames verbatim and stays mute to the router — the Pi is invisible. Pure L2, no interception.

L2 passthrough drop internet out-of-band muted
  • Server ⇄ router (verbatim). Frames cross eth0→br0→usb0 unchanged — the router sees the server's own MAC+IP, like an unplug/replug.
  • Server → drop (local). Only the server side reaches updrop at karasu.local / KARASU_IP, fenced off the router port.
  • Pi → router = dropped. ebtables OUTPUT -o usb0 DROP silences every Pi-origin frame. The Pi has no identity on the router side and no internet of its own.
  • You → Pi (out-of-band). Manage over wlan0, console, or a mgmt NIC — never the bridged wire.

Intercept mode

pi_intercept_setup.sh

Inline active MITM. A visible L3 host: br0 takes a corporate IP, and the workstation's web traffic is redirected into mitmproxy to rewrite one URL. AP + a mgmt cable stay for the ops laptop.

ordinary passthrough redirect → proxy proxy out / internet mgmt (AP + cable) dropped (QUIC)
  • Ordinary traffic. Workstation ⇄ corp switch bridges normally, keeping the workstation's own corporate IP; it browses as usual.
  • Matched web → proxy. Workstation :80 (+:443) is REDIRECTed into mitmproxy; the one target URL is replaced by the addon, everything else passes through.
  • Proxy outbound. mitmproxy's own connections leave from the Pi's corporate IP — this is why the box is visible, not stealthy.
  • You → Pi. Manage over the wlan0 AP or the mgmt cable (eth2, 10.73.0.1); the drop rides those too.
  • Caveats. HTTPS needs the proxy CA trusted on the target; QUIC/UDP-443 is dropped so HTTP/3 can't bypass; assumes no 802.1X and no PAC/VPN on the target.

Constant in all three modes

  • One device — hostname karasu, product Yatagarasu.
  • updrop — binds ::, serves the drop on whatever is up.
  • wlan0 AP — clients plane (AP) or out-of-band mgmt plane (bridge / intercept).
  • karasu.local — Avahi mDNS.
  • Provision once, then live ops — no reboot.

Pick by goal

  • Move files in the field with no infra → AP.
  • Add a file plane to a server's link, invisibly → Bridge.
  • Tamper with one web page on a test workstation → Intercept.
  • AP + cable management works in all three.

Non-negotiables (inline modes)

Members carry no IP (bridge)

A bridge member that keeps its own address makes the Pi half-route and leak. up flushes both and forces NetworkManager to release them.

Stealth vs visible is a choice

Bridge = the ebtables mute keeps the Pi silent. Intercept is the opposite — a visible host that NATs its own proxy traffic. Don't confuse the two.

Manage out-of-band

Drive up/down over console, wlan0, or the mgmt cable — never the inline wire, which flaps when the bridge builds.

Real uplink, not a tether

The upstream must be a real switch/router port. A single-client USB tether (one MAC, NAT) can't bridge a second host.

HTTPS costs trust (intercept)

Silent HTTPS rewrite needs the proxy CA installed on the target. QUIC is dropped and IPv6 skipped so nothing bypasses the TCP redirect.

Not for 802.1X ports

All inline modes assume passive MAC monitoring. An authenticating port needs EAPOL pass-through, or insertion err-disables it.
